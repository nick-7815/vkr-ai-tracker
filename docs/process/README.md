# Процесс ВКР: модели BPMN 2.0

Документация к предметной области: как выпускная работа проходит путь от перечня тем
до защиты сейчас и как этот путь выглядит после автоматизации.

| Файл | Что описывает |
|---|---|
| `vkr-process-as-is.bpmn` | «Как есть» — процесс кафедры по разбору с преподавателями |
| `vkr-process-to-be.bpmn` | «Как надо» — тот же процесс с ВКР-трекером и автопроверками |
| `as-is.js`, `to-be.js` | Описания моделей: узлы, потоки, координаты |
| `lib/bpmn-builder.js` | Генератор BPMN: раскладка, ломаные, DI, проверка пересечений |
| `preview.html` | Локальный просмотр обеих схем (нужен любой http-сервер) |

Схемы открываются в Camunda Modeler, на demo.bpmn.io, в Signavio, Bizagi и ELMA.

## Участники

Основной пул — кафедра. Внешние участники вынесены отдельными пулами, обмен идёт сообщениями.

| Роль | Что делает |
|---|---|
| Заместитель заведующего по учебной части | Владелец регламента: открывает цикл, назначает и правит даты этапов, контролирует ход процесса |
| Секретарь кафедры | Сводит темы, формирует приказ, отправляет его в ректорат, следит за сроками |
| Руководитель ВКР | Выписывает темы, согласовывает формулировку, проверяет замечания по коду |
| Студент | Выбирает тему, пишет работу, оформляет источники и документы, сшивает работу |
| Нормоконтролёр | Нормоконтроль по методичке и ручная проверка на антиплагиат со справкой |
| Заведующий кафедрой | Подписывает сшитую работу после предзащиты, перед защитой |
| Другие преподаватели | Просмотры, предзащита втроём, защита — не руководитель этого студента |
| Ректорат *(внешний)* | Подписывает приказ либо возвращает с замечаниями |
| Библиотека *(внешняя)* | Проверяет и подписывает список литературы |
| Источники метаданных *(внешние, только в «как надо»)* | Crossref, eLIBRARY, каталоги библиотек — откуда рефчекер берёт описания |

## Как заводятся темы

Таблица заполняется в два круга, и это разные вещи:

1. **Темы на выбор.** Секретарь собирает таблицу преподавателей, у которых в этом году есть дипломники;
   каждый вписывает свои темы — без фамилий, просто перечень, из которого студенты выбирают.
2. **Подача студента.** После того как студент и преподаватель договорились, преподаватель подаёт пару:
   фамилия студента и та формулировка темы, которая пойдёт в диплом. Она может отличаться от исходной —
   студент мог предложить свою тему или формулировку уточнили под специфику.

**Проект приказа** — то, что собрано из поданных пар и ещё не подписано, правки на этом этапе возможны.
**Приказ** — подписанный документ: темы и руководители закреплены, дальше тема меняется только по заявлению.

## Окна регламента

Даты задаёт заместитель заведующего по учебной части, и окна бывают двух видов:

- **Окно-период** — интервал дней: просмотры, нормоконтроль, приём документов. Внутри интервала студент
  и преподаватели должны созвониться или встретиться и выставить оценку. В модели «как надо» на такую
  задачу повешен граничный таймер: не успели к концу окна — трекер напоминает обеим сторонам и показывает
  просрочку замзаву. Сейчас за этим он следит вручную.
- **Окно-день** — конкретная дата с интервалом времени внутри: предзащита и защита, где студенты идут
  по слотам.

## Сроки

| Когда | Что |
|---|---|
| Начало года | Замзав задаёт даты цикла; таблица тем, подача студентов, проект приказа и приказ |
| Конец первого семестра | Список литературы |
| Зима | Первый просмотр — окно в несколько дней |
| Весна | Второй просмотр — окно в несколько дней |
| Март–апрель | Ревью кода, за 1–2 месяца до предзащиты |
| Перед предзащитой | Нормоконтроль, антиплагиат |
| Май | Предзащита — один день со слотами; затем подпись списка литературы, сшивание и подпись заведующего |
| После предзащиты | Защита |

## Что автоматизируется

Четыре направления, отмеченные в модели «как надо» дорожкой **ВКР-трекер**:

1. **Рефчекер литературы.** Студент даёт ссылку, DOI или ISBN — система находит метаданные и отдаёт
   готовое библиографическое описание по ГОСТ Р 7.0.5-2008. Строку остаётся вставить в свой список:
   формат работы не важен, а для работ на этом шаблоне запись сразу ложится в `bibliography/references.bib`
   со стилем `lib/csl/gost-r-705-2008-numeric.csl`. Отдельно проверяется состав списка: не менее 30 источников,
   не менее 20 % зарубежных, обязательные базы.
2. **LLM-ревью кода.** Код сдаётся отдельным архивом — в пояснительную записку он не вкладывается.
   Система распаковывает архив, разбирает проект и выдаёт замечания с привязкой к файлам и строкам;
   руководитель проверяет их и остаётся арбитром.
3. **Нормоконтроль по PDF.** Работа принимается в PDF: у большинства она сделана в Word, у части
   в Typst или LaTeX — единый вход убирает эту разницу. Формальные правила проверяются разбором PDF
   (состав и порядок разделов, поля, кегль и интервал, нумерация, ссылка в тексте на каждый источник),
   содержательные сверяет LLM с методичкой Кравца и Щербакова.
4. **Сам маршрут.** Цикл открывает заместитель заведующего по учебной части: выбирает окна регламента
   и при необходимости правит конкретные даты — дальше система сама раскладывает сроки по этапам и шлёт
   напоминания. Подвинуть дату можно в любой момент: для этого в модели есть отдельный событийный
   подпроцесс «Изменение дат по ходу цикла». Каталог тем, проект приказа, подбор рецензентов и статусы
   тоже ведёт трекер. Сейчас всё это замзав держит на себе вручную.

Что попадает в систему от студента: **PDF пояснительной записки**, **архив с кодом** и **список источников**,
который он набирает через рефчекер.

За людьми остаются: антиплагиат со справкой, просмотры, предзащита, подписи заведующего
и библиотеки, защита.

## Открытые вопросы

- Нужен ли живой нормоконтролёр после LLM-проверки — в модели он подтверждает результат.
- Когда список литературы уходит в библиотеку: в схеме это после антиплагиата, перед сбором пакета.
- Кто входит в комиссию на защите и участвует ли в ней заведующий помимо подписи.
- Точные даты просмотров и нормоконтроля.
- Нужен ли отдельный маршрут смены руководителя, а не только темы.

## Пересборка и проверки

```sh
cd docs/process
npm install
npm run build   # генерирует оба .bpmn из as-is.js и to-be.js
npm run check   # bpmn-moddle + bpmnlint по обеим моделям
```

`npm run build` попутно проверяет раскладку: линии не должны пересекать фигуры,
фигуры — накладываться, рамки этапов — рассекать элементы. Любая проблема печатается списком.

Локальный просмотр: `python3 -m http.server` в этой папке и открыть `preview.html`.
